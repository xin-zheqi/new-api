# Responses 重复工具调用编号兼容修复

用户反馈 DeepSeek 官方链路报 `Duplicate 'call_id': fc_0.`。源码中没有生成固定 `fc_0` 的逻辑，DeepSeek 渠道的 Responses 请求使用其原生 `/responses` 接口。现有工具结果补齐遇到重复编号会跳过，不能解决跨轮历史复用编号的情况。未取得生产原始请求，因此不能确认最初是客户端、中间转换还是上游响应生成了重复编号。

本地模拟了不同轮次复用 `fc_0` 的完整工具调用历史：上一发布镜像开启工具结果补齐后仍返回同样的 400；本次修复使可明确配对的历史通过。

## 修复范围

- 沿用渠道“工具结果补齐”开关，经典和新版前端入口不变，默认仍关闭。
- 只处理最终发往上游的 Responses 请求。正常唯一编号不会进入新增扫描；透传及其他最终协议保持原行为。
- 完整本地历史中，上一批工具均已有真实结果、每个结果可按原编号明确配对时，给后续重复调用及对应结果分配相同的新编号。重复的调用 item ID 同步修改，已有唯一 item ID 保留。
- 参数、真实结果（含空字符串和图片数组）、普通正文、明文思考、用量、模型映射、路由及计费规则均不修改。只处理请求历史，不改写上游当前响应里的工具编号，也不增加上游尝试。
- 存在远端历史标识、item reference、并行调用撞号、结果缺失或重复、跨用户轮次错配、未知引用、加密思考、需要更改签名调用/结果等歧义时，整段保持原样。这些请求仍可能报错。
- 扫描限制为 4096 个输入项、256 个调用和 256 个结果。先保留全部已有编号再生成新编号；修复可重复执行，结果稳定。无数据库、Redis、网络访问，只在实际修复时重建请求文本。
- 管理员日志在已有 `other.admin_info.tool_output_repair` 内增加可选 `renamed_calls` 计数，不存工具参数或结果。没有表结构、查询或 ORM 依赖变更。

## 验证

- 新增回归覆盖多轮和并行批次配对、反序结果、预留后续 ID、唯一 item ID、参数与真实结果保留、幂等、重试输入隔离、关闭和透传、其他最终协议、远端历史、签名/加密、歧义与数量上限。
- Go 1.26.10：根模块构建，`go test ./relay/... ./service -count=1`，`go test ./controller -count=1 -timeout=5m`，以及 `model` 包回归。控制器测试使用可执行的 tmpfs 临时目录，以避免 Docker 临时 SQLite 写盘延迟。
- 最终 Docker 镜像接本地模拟上游：26 项检查、34 次上游请求。覆盖 DeepSeek/OpenAI 两种渠道、思考开关、流式/非流式、连续四轮复用编号、关闭/透传、远端和不安全历史保持原样、成功日志数量与原始用量、管理员修复计数。每次下游请求只有一次上游请求。
