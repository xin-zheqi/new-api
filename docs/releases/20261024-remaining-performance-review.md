# 后续性能优化评估（2026-10-24）

本轮为源码检查和固定样本基准测量，没有修改生产代码或发布新的 Docker。
当前已发布版本仍为 `config-cache-20261024`。

## 1. 优先处理：Responses 请求深拷贝

`relay/responses_request.go:37` 在每次准备上游请求时调用
`common.DeepCopy`。它使用 `jinzhu/copier v0.4.0` 的反射深拷贝。
Responses 的 `input`、`tools` 等字段是 `json.RawMessage`（字节切片）。
依赖的切片复制路径逐元素执行反射处理，没有专门的字节块复制路径。

固定请求仅包含模型、reasoning 和一条长 user 输入，测量三个样本的中位数：

| 输入正文大小 | 仅深拷贝耗时 | 分配次数/请求 | 分配字节/请求 |
| --- | ---: | ---: | ---: |
| 16 KiB | 0.868 ms | 16,443 | 约 37 KB |
| 256 KiB | 12.971 ms | 262,203 | 约 535 KB |
| 1 MiB | 51.053 ms | 1,048,635 | 约 2.11 MB |

这里最值得减少的是逐字节反射和小对象分配。对于长历史/工具结果以及
高并发请求，这会增加准备请求时的 CPU 成本和垃圾回收压力。

可以优先验证对 `json.RawMessage`/字节切片使用批量深复制的方案。
副本仍必须独立，不能简单改成浅拷贝；必须验证显式零值、nil/空值、
嵌套字段、原始 JSON 字节、encrypted_content、重试输入隔离，以及映射/
参数覆盖/思考修复不能反向修改原始请求。暂未实现，因此不声称改善后的速度。

另一个可评估的点：Responses 和 Chat 的透传判断位于深拷贝之后；透传
最后使用原始 BodyStorage，却已支付 DTO 拷贝成本。移动判断仍须保留当前
模型映射校验、后缀处理及适配器初始化语义，不能直接删除前面的步骤。

## 2. 按需历史修复：重复复制整段 JSON

`NormalizeDeepSeekSchemas`、`RepairReasoningRequest`、
`RepairToolOutputRequest` 分别使用 `gjson.ParseBytes(data)`，每次会构造
整个请求的字符串副本。重复工具 ID 修复、修复后重新解析还可能增加次数。

固定 DeepSeek Responses 请求，只有一条 user 消息，无工具和待修复历史：

| 输入正文大小 | 两个修复开关关闭 | 两个修复开关开启 | 开启后的分配字节 |
| --- | ---: | ---: | ---: |
| 16 KiB | 0.009 ms | 0.061 ms | 约 55 KB |
| 256 KiB | 0.142 ms | 0.953 ms | 约 811 KB |
| 1 MiB | 0.534 ms | 3.929 ms | 约 3.17 MB |

两种配置均包含 DeepSeek schema 兼容检查，因此关闭列不是 OpenAI 普通
请求的开销。开启列测量的是仍需扫描但最终没有改写的请求，不能推断为
复杂历史修复的上限。可以评估复用只读解析输入、减少重复副本；有改写后
必须重新建立正确的偏移，不能跳过保护字段或原有修复规则。

## 3. 大屏蔽词词典：重复计算匹配器缓存键

`service/str.go` 已缓存 AC 匹配器，但 `getOrBuildAC` 仍在每次查缓存前
执行小写/去空白、排序和哈希。固定短文本无命中、匹配器预热后的中位数：

| 配置词数 | 一次检查耗时 | 分配字节/检查 |
| --- | ---: | ---: |
| 1 | 0.412 µs | 216 B |
| 1,000 | 39.190 µs | 约 16.6 KB |
| 5,000 | 180.984 µs | 约 82.2 KB |

适合在配置变化时构造不可变词典快照并更新匹配器，避免请求阶段反复排序。
调用方还包括渠道自动禁用关键词，必须防止不同词典互相污染并保留热更新
语义。空词典目前已跳过检查，不会产生表中大词典的开销。

## 4. 流式转换诊断反复处理

`service/response_converter.go` 每个流片段调用 `state.Diagnostics()`。
后者复制累计诊断切片，`RecordConversionDiagnostics` 随后再次逐项去重。
如果前面产生了转换诊断，即使后续纯文本片段没有新诊断也会重复执行。
没有诊断时已有 nil 快速路径。

可以按新增诊断增量记录，但必须覆盖无输出事件、转换失败、结束事件和
日志截断，不能仅依赖成功输出中附带的诊断而漏记。这一项本轮确认了代码
路径，没有测量耗时，预计更偏向大量流片段下的分配优化。

## 5. 非流式空响应检查后，协议处理器再次读取和解析正文

`validateUpstreamTextBody` 先 `io.ReadAll`，将正文放回 `resp.Body`，并用
通用 JSON 对象检查空响应。OpenAI Responses/Chat 处理器随后再次
`io.ReadAll` 和解码 DTO。这里存在可复用的缓冲区和重复解析。

可以先评估复用已读取字节，保留原有校验和协议处理顺序。完整共用解析
结果涉及协议和错误分类，风险更高。此项主要影响较大的非流式响应；
流式前缀缓冲服务于安全重试，不能直接删除。尚未进行此项的性能测量。

## 测量范围与建议顺序

环境为 Linux/amd64 Docker、Go 1.26.10、i7-13700K，命令：

```text
go test ./service -run '^$' -bench '^BenchmarkReview' -benchmem -benchtime=300ms -count=3
```

临时 benchmark 只复制进隔离容器，没有加入生产包。
样本、依赖源码检查副本及日志保留在 `.local-tests/remaining-perf-20261024/`。
镜像为现有 `newapi-config-cache-test:20261024`；本轮测量的深拷贝、词典及
历史修复生产文件与当前工作区内容一致。所有数字都是局部 CPU/分配成本，
不是生产端到端延时，也不能相加当作所有请求的固定开销。

建议首先验证字节切片深复制，其次处理大请求的重复 JSON 副本；流式诊断
和大词典缓存键可以单独做小改动。数据库审计策略缓存、订阅状态缓存及
鉴权/余额缓存还涉及跨实例一致性，继续作为独立评估项，不宜与本轮
CPU 热路径优化混合实施。

## 补充：批量深复制原型对比

用户询问预期收益后，在隔离容器中加入测试专用原型：通过 copier 的
TypeConverter 对 `json.RawMessage` 和 `[]byte` 使用 `bytes.Clone`，其余
字段仍采用原有深拷贝。未修改 `common/copy.go` 或任何生产文件。

同一容器、同一固定请求、每项三次采样，以下为中位数：

| 输入正文大小 | 当前深拷贝 | 批量复制原型 | 单次减少 |
| --- | ---: | ---: | ---: |
| 空正文（仍有 30 字节 input JSON） | 0.01173 ms | 0.01053 ms | 约 0.0012 ms |
| 16 KiB | 0.85168 ms | 0.01217 ms | 约 0.84 ms |
| 256 KiB | 12.93368 ms | 0.04083 ms | 约 12.89 ms |
| 1 MiB | 52.20213 ms | 0.12215 ms | 约 52.08 ms |

16 KiB、256 KiB、1 MiB 的拷贝步骤分别约快 70、317、427 倍。
1 MiB 样本分配次数从 1,048,635 降为 33，分配字节从约 2.11 MB 降为
1.06 MB。原型仍有转换器映射的固定开销，空正文样本分配字节从 2640 B
上升到 3888 B，不能概括为所有请求都减少同样比例的内存或耗时。

测试验证了 RawMessage 的 nil/非 nil 空值、原始 JSON、合成密文、显式
零值/false 与当前实现一致，并确认修改副本的历史、工具、reasoning 和
标量指针不会修改原始请求。这是局部原型验证，尚不是完整生产回归。

```text
go test ./service -run '^TestBulkCopyPrototype' -bench '^BenchmarkBulkCopyComparison' -benchmem -benchtime=500ms -count=3
```

命令通过；原型文件和日志分别位于本次证据目录的
`bulk_copy_prototype_test.go`、`bulk-copy-comparison.log`。

这些倍数只描述拷贝步骤。假设一次请求总首 token 等待为 2 秒，且恰有
一次约 52 ms 的此类拷贝，节省约 52 ms 相当于总等待减少约 2.6%，
不代表整次请求快 427 倍。上游推理速度不受这个本地优化直接改变。
高并发下可能进一步降低 CPU/GC 排队，但未做并发端到端压测，不量化
吞吐提升，也不把本地原型结果当作生产承诺。

## 补充：2 核 / 2 GiB 容器限额

在同一 i7-13700K 主机上，将隔离容器限制为 `--cpus 2 --memory 2g
--memory-swap 2g`，先完成编译再施加限额，执行相同测试二进制。确认
NanoCpus=2000000000、Memory=2147483648、MemorySwap=2147483648，Go
benchmark 后缀为 `-2`。三次样本中位数如下：

| 输入正文大小 | 当前拷贝 | 批量原型 | 单次节省 |
| --- | ---: | ---: | ---: |
| 256 KiB | 13.325 ms | 0.057 ms | 13.268 ms |
| 1 MiB | 52.829 ms | 0.157 ms | 52.672 ms |

原型内容/隔离测试及 benchmark 均通过，日志为
`.local-tests/remaining-perf-20261024/bulk-copy-2c2g.log`。
这只模拟 CPU 配额和内存容量，物理 CPU 仍是 i7-13700K，也没有加入
生产并发流量。拷贝主要是单线程工作，限制为两个核不会自动把其耗时
按主机核心数比例放大；2 GiB 容量本身也不代表更低的内存带宽。
因此，此结果不能代表任意一台共享型 2 vCPU 云主机。
